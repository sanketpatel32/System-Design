# SLO (Service Level Objective)
> **Category:** Observability

---

### Overview
A **Service Level Objective (SLO)** is a target value or range of values for a Service Level Indicator (SLI) over a specified time window (e.g., 30 rolling days). SLOs set the internal reliability standard that engineering teams commit to achieving.

### Core Structure of an SLO
An SLO definition must explicitly specify:
1. **Target SLI**: The metric being evaluated (e.g., Availability, Latency).
2. **Target Percentage**: The goal threshold (e.g., 99.9%).
3. **Time Window**: Rolling period (e.g., 30 days) or calendar period (e.g., Monthly).

$$\text{SLO Target: } \text{SLI} \ge T\% \quad \text{over Window } W$$

### Best Practices for Designing SLOs
- **Tiered Objectives**: Set separate internal SLOs (stricter) vs external SLAs (more lenient) to create a buffer.
- **User-Centric Selection**: Focus SLOs on metrics that directly impact user journey (e.g., checkout page latency vs background log ingestion).
- **Avoid 100% SLO**: 100% SLO is unachievable, prevents innovation, and incurs exponential infrastructure costs.

### Key takeaway
An **SLO** defines the boundary between acceptable performance and unacceptable degradation. Internal SLOs should always be stricter than external SLAs to allow remediation before breach penalties occur.
