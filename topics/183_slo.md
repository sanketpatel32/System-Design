# SLO (Service Level Objective)
> **Category:** Observability

---

### Overview
A **Service Level Objective (SLO)** is a target reliability value or range set for a specific Service Level Indicator (SLI) over a designated rolling timeframe (e.g., 99.9% availability over 30 days). SLOs serve as the official operational agreement between engineering teams, product managers, and business leadership regarding how reliable a service must be.

Setting realistic SLOs prevents over-engineering: aiming for 100% uptime is exponentially expensive and hinders developer velocity.

### Mathematical SLO Alignment
An SLO defines the boundary line for acceptable operational behavior:

$$\text{Observed SLI} \ge \text{Target SLO}$$

For instance, an e-commerce checkout service might set two distinct SLOs:
1. **Availability SLO:** $99.95\%$ of valid checkout HTTP requests return `200 OK` over a rolling 30-day window.
2. **Latency SLO:** $99.0\%$ of valid checkout HTTP requests complete in $< 300\text{ms}$ over a rolling 30-day window.

### SLO Definition Specification & API Contract

| Endpoint / Config | Method | Payload / Response | Description |
|---|---|---|---|
| `POST /api/v1/slo` | POST | `{"service": "checkout", "metric": "latency", "target": 0.99, "threshold_ms": 300, "window": "30d"}` | Registers a new SLO definition into the observability engine. |
| `GET /api/v1/slo/status` | GET | `{"service": "checkout", "sli_current": 0.994, "slo_target": 0.99, "status": "COMPLIANT"}` | Fetches real-time compliance status for service SLOs. |

### SLO Storage Schema & Data Model

| Field Name | Data Type | Engine | Purpose |
|---|---|---|---|
| `slo_id` | UUID | PostgreSQL / MySQL | Primary identifier for the target SLO rule. |
| `service_name` | String | PostgreSQL | Microservice bound to the SLO. |
| `sli_type` | Enum | Relational DB | Type of indicator (`LATENCY`, `AVAILABILITY`, `THROUGHPUT`). |
| `target_percentage` | Double (e.g. 99.9) | Relational DB | The numeric SLO target threshold. |
| `evaluation_window` | String (e.g. `30d`)| Relational DB | Sliding time window evaluated continuously. |
| `alert_routing_key` | String | Relational DB | PagerDuty or webhook routing endpoint. |

### Architectural Trade-offs

| Strategy / Choice | Advantages | Disadvantages | Best Used When |
|---|---|---|---|
| **Tight SLOs (e.g., 99.99%)** | Maximizes customer satisfaction and enterprise reliability guarantees. | Massive infrastructure cost; restricts release frequency and rapid feature deployment. | Core financial ledgers, identity providers, and healthcare APIs. |
| **Realistic / Moderate SLOs (99.0% - 99.9%)** | Balances customer needs with engineering agility; leaves room for frequent CI/CD releases. | Occasional transient errors might impact sensitive edge-case users. | Typical SaaS web applications and e-commerce platforms. |
| **Single-Window Alerting** | Extremely simple to set up in Prometheus alert rules. | Causes high false-positive pages during short bursts and delays alerting on sustained slow burns. | Non-critical internal tooling and dev environments. |

### Key takeaway
An **SLO** defines the target threshold of acceptable performance for an SLI. It acts as an operational contract that prevents unachievable perfection goals, aligns engineering velocity with user expectations, and powers multi-window burn rate alerts.
