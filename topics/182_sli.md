# SLI

> **Category:** Observability

---

SLI = **Service Level Indicator** — a quantitative measure of service quality.

### Definition
> "A carefully defined quantitative measure of some aspect of the level of service that is
> provided." — Google SRE Book

### Examples
- **Availability**: fraction of successful HTTP requests.
- **Latency**: p99 of request duration.
- **Throughput**: requests served per second.
- **Freshness**: time since last data update.
- **Correctness**: fraction of correct results.
- **Durability**: fraction of data preserved.

### Good SLIs
- **User-facing**: measures what users experience.
- **Measurable**: directly observable from system.
- **Actionable**: team can influence it.

### Bad SLIs
- CPU utilization (cause, not symptom).
- Uptime of a single instance (doesn't capture user impact).
- Internal queue depth (not user-facing).

### Structure
```
SLI = (good events) / (total events) over a window
```
Example: "99.5% of HTTP requests returned 2xx in the last 28 days."

### Choosing SLIs
1. Identify user journeys.
2. Define what "good" looks like for each.
3. Pick measurable indicators.
4. Set targets (SLOs).

### Multiple SLIs
A service often has multiple:
- **Latency SLI**: 99% of requests < 500ms.
- **Availability SLI**: 99.9% return 2xx.
- **Freshness SLI**: 95% of data updated within 1 min.

### Common mistake
Too many SLIs. Pick 3-5 that capture user experience. Don't drown in metrics.

### Key takeaway
SLIs are quantitative measures of user experience. Pick 3-5 user-facing indicators (latency,
availability, freshness). Measure them as "good events / total events." SLOs are targets for
SLIs.
