# OAuth 2.0
> **Category:** Security

---

### Overview
**OAuth 2.0** (RFC 6749) is the industry-standard delegated authorization framework that enables a third-party application to obtain limited access to a user's HTTP service resource without exposing the user's plain-text credentials. It separates the role of the resource owner from the client by introducing an authorization layer and issuing access tokens.

Modern implementations mandate the **Authorization Code Grant with PKCE (Proof Key for Code Exchange)** (RFC 7636) to prevent authorization code injection attacks on native mobile and single-page web applications.

### Authorization Code Flow with PKCE Topology

```
+--------+                               +-------------------------------+
|        |-- 1. Authorization Request -->|                               |
|        |   + PKCE Code Challenge       |                               |
|        |<-- 2. Authorization Code -----|                               |
|        |                               |                               |
| Client |                               | Authorization Server (Auth0)  |
| App    |-- 3. Token Request ---------->|                               |
|        |   + Auth Code + Code Verifier |                               |
|        |<-- 4. Access & ID Token ------|                               |
+--------+                               +-------------------------------+
    |                                                    
    | 5. Request Resource (Bearer Token)                
    v                                                   
+------------------------------------------------------------------------+
| Resource Server / API Gateway (Validates Access Token Claims & Scopes) |
+------------------------------------------------------------------------+
```

### Core OAuth 2.0 Grant Types Comparison

| Grant Type | Use Case / Environment | Security Level | Recommended Protocol |
|---|---|---|---|
| **Authorization Code + PKCE** | Mobile Apps, SPAs, Web Frontends | Highest | Standard for all client applications. |
| **Client Credentials** | Machine-to-Machine (M2M) Microservices | High (Server-to-Server) | Used when no end-user interaction exists. |
| **Implicit Grant** | Legacy Single Page Applications | **Deprecate** (Insecure)| Replaced by Authorization Code + PKCE. |
| **Resource Owner Password** | Legacy Internal System Migration | **Deprecate** (Insecure)| Exposes user credentials to client apps. |

### OAuth 2.0 Token API Interface Specifications

| Endpoint | Method | Request Body / Parameters | Response Payload |
|---|---|---|---|
| `/oauth/authorize` | GET | `client_id`, `redirect_uri`, `scope`, `code_challenge`, `code_challenge_method=S256` | Redirects to `redirect_uri?code=AUTH_CODE_123` |
| `/oauth/token` | POST | `grant_type=authorization_code`, `code`, `redirect_uri`, `code_verifier`, `client_id` | `{"access_token": "eyJ...", "token_type": "Bearer", "expires_in": 3600, "refresh_token": "r_99"}` |
| `/oauth/introspect`| POST | `token=eyJ...`, `client_id`, `client_secret` | `{"active": true, "scope": "read write", "client_id": "app_1", "exp": 1700000000}` |

### OAuth 2.0 Client & Token Data Schema

| Field Name | Data Type | Storage Engine | Purpose |
|---|---|---|---|
| `client_id` | String (Indexed) | PostgreSQL / Spanner | Unique public identifier for the registered third-party application. |
| `client_secret_hash` | String | Relational DB | Hashed secret for confidential server-side clients (M2M). |
| `redirect_uris` | Array of Strings | Relational DB | Explicit list of whitelisted redirection URLs. |
| `allowed_scopes` | Array of Strings | Relational DB | Whitelisted scope permissions (e.g., `["read:profile", "write:orders"]`). |
| `auth_code_hash` | String | Redis Cache | Temporary, single-use hashed auth code (TTL: 60s). |

### Architectural Trade-offs

| Strategy / Choice | Advantages | Disadvantages | Best Used When |
|---|---|---|---|
| **Authorization Code + PKCE** | Cryptographically prevents auth code interception; works securely without client secret. | Requires client-side hashing (`SHA-256` code verifier logic). | All public native apps, mobile devices, and single-page apps (SPAs). |
| **Opaque Tokens + Introspection** | Revocable instantly by Authorization Server; hides internal token payload. | Every API call requires an external HTTP introspection call to Auth Server. | High-security corporate enterprise APIs. |
| **Self-Contained JWT Access Tokens** | Stateless verification at microservices without Auth Server lookups. | Revocation lag; access token valid until expiration unless blacklisted. | Microservice architectures requiring horizontal scale. |

### Key takeaway
**OAuth 2.0** delegates authorization securely using scoped tokens. Implement **Authorization Code Grant with PKCE** for user-facing applications and **Client Credentials** for server-to-server microservice communication.
