# SLA

> **Category:** Observability

---

SLA = **Service Level Agreement** — a formal contract with customers about reliability.
Breaking it has consequences (refunds, credits).

### Definition
> "An explicit or implicit contract with your users that includes consequences if you fail to
> deliver." — Google SRE Book

### Examples
- "99.9% availability monthly. If below, customer gets 10% refund."
- "p99 latency < 200ms. If exceeded for 3 days, escalate."
- "Support response < 4 business hours. Else, SLA breach."

### Components
1. **SLI** (what you measure).
2. **Target** (the value).
3. **Window** (monthly, annual).
4. **Consequence** (refund, credit, escalation).

### SLA vs SLO
| | SLA | SLO |
|--|-----|-----|
| Audience | Customers | Internal team |
| Consequence | Financial / legal | Process changes |
| Strictness | Looser | Stricter |

SLO is always stricter than SLA — leaves buffer.

### Common SLAs (cloud)
- AWS S3: 99.9% availability; < that = 10% credit.
- AWS EC2: 99.99% region availability.
- GCP GCS: 99.9% multi-region.

### Drafting an SLA
1. Identify what users care about.
2. Pick realistic targets (below your SLO).
3. Define exclusions (force majeure, customer-caused).
4. Specify remedies.
5. Get legal review.

### Why SLAs matter
- **Customer trust**: clear expectations.
- **Differentiation**: premium SLA = premium price.
- **Accountability**: forces engineering to deliver.
- **Legal protection**: defines when you owe refunds.

### Key takeaway
SLAs are contracts with customers. Set them **looser** than internal SLOs (buffer). Specify the
SLI, target, window, and remedy. They build trust and create accountability.
