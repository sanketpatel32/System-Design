# OAuth 2.0

> **Category:** Security

---

OAuth 2.0 = **a protocol for delegated authorization** — letting a user grant a third-party
app access to their data on another service, without sharing their password.

### Use case
"Log in with Google" / "Give this app access to my GitHub repos."

### Roles
- **Resource Owner**: the user.
- **Client**: the third-party app wanting access.
- **Authorization Server**: issues tokens (Google, GitHub).
- **Resource Server**: has the user's data (Gmail API, GitHub API).

### Authorization Code flow (most common for web apps)
```
1. User clicks "Log in with Google."
2. App redirects user to Google's auth page.
3. User logs in, grants permission.
4. Google redirects back to app with an authorization code.
5. App exchanges code for access token (server-to-server).
6. App uses access token to call Google APIs on user's behalf.
```

### Tokens
- **Access token**: short-lived, used to call APIs.
- **Refresh token**: long-lived, used to get new access tokens.
- **ID token** (OIDC extension): identity claims (user info).

### OIDC (OpenID Connect)
- Built on OAuth 2.0.
- Adds **authentication** (proves who the user is).
- Adds **ID token** with user identity.
- "Log in with X" usually means OIDC.

### Other flows
- **Client Credentials**: machine-to-machine (no user).
- **Device Code**: smart TVs, IoT.
- **PKCE**: for mobile/SPA (no client secret).

### Scopes
- Permissions requested (e.g. `read:user`, `repo`).
- User consents to specific scopes.
- Token only does what scopes allow.

### Security
- Always use **HTTPS**.
- Validate **state** parameter (CSRF protection).
- Use **PKCE** for public clients.
- Store tokens securely.
- Don't leak client secrets.

### Key takeaway
OAuth 2.0 lets users grant third-party apps access without sharing passwords. **Authorization
Code flow with PKCE** is the modern standard for web/mobile. OIDC adds authentication on top.
Always validate state, use HTTPS.
