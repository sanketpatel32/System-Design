# SLO

> **Category:** Observability

---

SLO = **Service Level Objective** — a target value for an SLI, measured over a window.

### Definition
> "A target value or range of values for a service level that is measured by an SLI." — Google
> SRE Book

### Example
- **SLI**: 99.5% of HTTP requests return 2xx.
- **SLO**: target = 99.9% availability over 30 days.
- **Error budget**: 0.1% of 30 days = 43 min downtime allowed.

### Why SLOs
- Quantify reliability expectations.
- Drive prioritization (reliability vs features).
- Form the basis for error budgets.
- Empower teams to make trade-offs.

### Setting SLOs
1. **Identify critical user journeys**.
2. **Define SLIs**.
3. **Pick targets** (based on user expectations, past performance).
4. **Set window** (28 days rolling is common).
5. **Track error budget**.

### Target levels
- 99% : dev / internal tooling.
- 99.9% : typical user-facing app.
- 99.99% : critical (payments, auth).
- 99.999% : ultra-critical (life support, telecom).

### Realistic targets
- Each "9" costs ~10x more engineering.
- 99.999% requires multi-region active-active.
- Don't over-commit.

### SLO vs SLA
- **SLO** (internal): what you aim for.
- **SLA** (external contract): what you promise customers.
- SLO > SLA: leave buffer.

### Review
- SLOs aren't set forever.
- Review quarterly.
- Adjust based on user feedback, business needs.

### Key takeaway
SLOs are reliability targets for user-facing SLIs. Set them stricter than SLAs. Track error
budgets to balance velocity vs reliability. Review quarterly. Start with conservative targets
and tighten as you mature.
